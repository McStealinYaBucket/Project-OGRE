## Failures

- 0x00873b10 `lua_exception::~lua_exception() (_ZN13lua_exceptionD2Ev)` (callgraph (OUT OF SAMPLE, found while checking sampled row 0x0087f8f0)): The body is lua_settop(L, idx): 75 bytes, 145 callers, no callees. It holds Lua 5.1's settop loop: if idx<0 then L->top += idx+1, else it writes nil up to base+idx. Every Lua Bridge registerClass in the sample ends with a call to it with (L,-2), which is lua_pop. The paired D0 at 0x008aad80 (rtti-slot, correct) shows why the pairing went wrong. MSVC inlined the D2 body into the scalar deleting destructor: it stores the vftable, then calls 0x00873b10(L,-2), then std::exception::~exception, then operator delete. So the 'only unpaired callee of the paired D0' was lua_settop, not a D2.
- 0x005283e0 `RBX::Name const& RBX::Name::declare<RBX::sSocialService>()` (callgraph (OUT OF SAMPLE, callee of sampled row 0x0052f610)): The body is doDeclare<sSocialService>: a static-local guard (dword_DD9E88 bit 1) around Name::declare(char const* const&), 99 bytes. On clang, declare<sX> is a different function: call_once(callDoDeclare<sX>), then doDeclare<sX> or getNullName. iOS 0x44e784 is 66 bytes and Mac 0x2f7178 is 65 bytes. On PLAYER that wrapper is inlined into isNullClassName 0x0052f610, which calls boost::call_once 0x0040c2c0 with a j_ thunk to 0x005283e0 and then calls 0x005283e0 directly. The same mistake covers 44 rows: 40 'Name::declare<>' rows on the 99-byte/5-block/1-callee doDeclare shape (callgraph and callgraph-guess, e.g. 0x00480b80, 0x00480cd0, 0x00480db0) and 4 on the 114-byte variant (e.g. 0x00427910, which I decompiled and which is the same static-guard body as doDeclare 0x00413740). 224 other bodies with the same shapes are named doDeclare<> (191 + 33).
- 0x00528650 `boost::spirit::classic::parser_error<std::string, __gnu_cxx::__normal_iterator<char*, std::vector<char>>>::what() const` (string-unique (IN SAMPLE, counted correct: name defect only)): The pairing is right: a 6-byte function returning 'BOOST_SPIRIT_CLASSIC_NS::parser_error', in the vftable of PLAYER's only instantiation (??_7?$parser_error@...V?$_Vector_iterator@DV?$allocator@D@std@@@2@@classic@spirit@boost@@6B@ at 0x00b121f0). The name is still not the Windows name, because the template argument is the libstdc++ iterator. On MSVC it is std::_Vector_iterator<char, std::allocator<char>>. 19 proposed rows carry libstdc++-only types (__gnu_cxx, std::_Rb_tree, std::_Ios_*, _List_base and so on): 8 string-unique, 10 callgraph, 1 callgraph-guess.

## Systematic causes

- No string-class rule produced a wrong pairing in the 60-row sample. That includes the high-risk cases: one-string string-set keys ('Size', 'void', 'Event', 'base', 'Steer'), short unique strings ('Signals', 'Content', 'HeadWeld', 'no value', '%.20g'), and asserts inlined from headers (Set.h:122/123, object.h:236/244/250/360). In every case the string sits in the function the oracle names. One example: the PLAYER Set<RobloxExtraSpace>::Iterator::operator-> lacks the Set.h:88 assert, but it calls 0x0066ff00 (Hook::is_linked), which holds it. Expected mismatches, which are platform or compiler differences and not wrong pairings: MSVC tail-merges 'INF' into '-INF'; StringConverter<double>::convertToString at 0x0074f700 has no NaN branch (consistent with /fp:fast); Ogre::SaveRBXDbgInfo uses a shorter vendor list; Http::get at 0x00623310 has a Windows-only Http.cpp:100 assert (816 vs 212 bytes on iOS). Population caller check (tools/check_string_pair_callers.py) over all 2,196 string rows: 2,943 row/oracle pairs agree with the oracle's callers or callers' callers, 55 disagree, and 569 have no named caller. The disagreements I looked at come from Mac Studio's different renderer (ViewRbxGfx/FastCluster callers), from the EnumDesc/Singleton::doGetSingleton wrapper chain, or from Lua static helpers. I traced none of them to a wrong body.
- The callgraph class pairs an inlined wrapper's name with the body of its callee (out of the string lens, but it is the main source of wrong names found here). When clang keeps a wrapper W out of line and MSVC inlines W into the paired caller, the single remaining unpaired PLAYER callee is W's own callee, and it receives W's name. Confirmed in two forms: (a) Name::declare<sX> (clang: the call_once wrapper; MSVC: inlined) gets the name on doDeclare<sX> bodies, 44 rows; (b) a D0's D2 that MSVC inlined into the scalar deleting destructor, so the D2 name goes to whatever the D2 called. Example: lua_settop 0x00873b10, 145 callers, named lua_exception::~lua_exception(). Of 155 D1/D2 names given as 'callee of paired D0', 8 bodies store no vftable at all and are candidates for the same error: 0x0044cdd0, 0x00496a40, 0x005b94b0, 0x005c5cc0, 0x005c6450, 0x005dada0, 0x00873b10, 0x00970b70. Only 0x00873b10 was decompiled and confirmed. Suggested fix: a callgraph candidate must not be accepted when the oracle partner is a wrapper whose own callee is the PLAYER candidate's shape match. For destructors, require a vftable store or a base-dtor call before naming a body as D1/D2.
- Names are copied verbatim from Itanium symbols, so 19 rows carry libstdc++-only template arguments (e.g. 0x00528650, whose PLAYER vftable says std::_Vector_iterator<char>). The pairing is right but the name is not the Windows name. These need rewriting from PLAYER's RTTI or flagging before they go into ida/PLAYER.i64 or source.
- Tooling: tools/ida/decomp_dump.py fails at exit on IDA 9.4 with `idaapi.cvar.database_flags |= idaapi.DBFL_KILL` (TypeError: cvar.database_flags is None). Its output is written first, but the kill flag is never set, so the database is left unpacked (.id0/.id1/.nam/.til). That is harmless on a scratch copy and dangerous on a canonical .i64. The fix the harness gives (set idaapi.DBFL_KILL through ida_loader / set_database_flag) has not been applied; I did not edit the script.
